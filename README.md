# OneVentOne

ระบบจัดการอีเวนท์หนึ่งธุรกิจต่อการติดตั้ง กรณีศึกษาร้านมงคลบาร์ สำหรับบริษัท มีพร้อม พัฒนาด้วย Next.js App Router + TypeScript + Prisma 6.19.3 + MongoDB replica set

รองรับโต๊ะเหมา ที่นั่ง และบัตรยืนหลายราคาที่ใช้โควตาร่วม การพักสิทธิ์ 15 นาที ส่งหลักฐานโอนเงิน ตรวจเงินจริงโดยเจ้าหน้าที่ ออกบัตรหลังอนุมัติ เช็กอินครั้งเดียว และบันทึกการคืนเงินที่ดำเนินการภายนอกระบบ ต้องเข้าสู่ระบบก่อนเริ่มจอง หากยังไม่มีบัญชีสามารถสมัครแล้วกลับมาเลือกบัตรงานเดิมได้

## เริ่มในเครื่อง Windows

ต้องมี Node.js 24 และ npm อินเทอร์เน็ตจำเป็นครั้งแรกสำหรับดาวน์โหลด MongoDB binary และ dependencies

```powershell
cd D:\one-vent-one
npm ci
npm run setup:local
npm run dev
```

`npm run dev` สร้าง Prisma client เปิด MongoDB ในเครื่อง รอจนฐานข้อมูลพร้อม แล้วเปิด Next.js ใน terminal เดียว กด Ctrl+C เพื่อปิดเว็บและฐานข้อมูลที่คำสั่งนี้เปิด ข้อมูลเดิมยังอยู่ใน `.local/mongodb` ถ้ามี MongoDB ที่พอร์ต 27018 เปิดอยู่แล้ว ระบบจะตรวจและใช้ตัวเดิมโดยไม่ปิดให้เมื่อหยุดเว็บ หาก `DATABASE_URL` ชี้ Atlas หรือฐานข้อมูลอื่นนอก local replica set ข้างต้น ระบบจะใช้ตามค่านั้นและไม่เปิด MongoDB เพิ่ม สำหรับ Docker ให้เปิด container ก่อนรัน dev เพื่อใช้ฐานข้อมูลใน container

ครั้งต่อไปใช้ `npm run dev` คำสั่งเดียว หากต้องการแยกเปิดเอง ยังใช้ `npm run db:dev` สำหรับฐานข้อมูล และ `npm run dev:web` สำหรับเว็บได้ ส่งตัวเลือก Next.js ต่อท้ายได้ตามเดิม เช่น `npm run dev -- --port 3001`

ครั้งแรกเท่านั้น เปิดอีก terminal โดยคง `npm run dev` ไว้ เพื่อเตรียม schema และข้อมูลเริ่มต้น:

```powershell
npm run db:validate
npm run db:push
npm run db:seed
```

เปิด [OneVentOne ในเครื่อง](http://127.0.0.1:3000) ระหว่างพัฒนาเปิดด้วย `localhost:3000` ได้เช่นกัน ที่อยู่อื่น (เช่น IP ในวง LAN) ต้องเพิ่มใน `TRUSTED_ORIGINS` มิฉะนั้นเข้าสู่ระบบจะขึ้น Invalid origin ข้อมูล MongoDB เก็บถาวรใน `.local/mongodb` (แยกกันในแต่ละเครื่อง บัญชีที่สร้างในเครื่องหนึ่งจะไม่มีในอีกเครื่อง) และหลักฐานใน `.local/uploads` คำสั่ง seed รันซ้ำโดยไม่รีเซ็ตราคา ผัง หรือการจองเดิม

`setup:local` สร้าง `.env` และกุญแจสุ่มแยกกันครั้งแรกเท่านั้น ไม่พิมพ์กุญแจและไม่เขียนทับไฟล์เดิม ถ้ามี `.env` แล้วให้ตรวจค่าด้วยตัวเอง `.env` และ `.local` ถูกตัดออกจาก Git

หาก npm แจ้งบล็อก install scripts: `prisma generate` และ `db:dev` จะทำขั้นตอนที่จำเป็นโดยตรง ตรวจ error จริงก่อนอนุญาตสคริปต์เพิ่มเติม ไม่ต้องอัปเกรด Prisma เป็น v7

`npm run dev` สร้าง Prisma client ใหม่ให้อัตโนมัติก่อนเปิดทุกครั้ง หลัง `git pull` จึงไม่ต้องรัน generate เอง ถ้าแก้ `prisma/schema.prisma` ระหว่างที่ dev เปิดอยู่ ให้รัน `npm run db:generate` (ใช้ได้แม้ dev เปิดอยู่ ไม่ขึ้น EPERM แล้ว) จากนั้นปิดและเปิด `npm run dev` ใหม่ เพราะ server ที่รันอยู่ยังจำ client เดิมไว้

## สร้างผู้ดูแลครั้งแรก

เปิดระบบไว้ (`npm run dev` หรือเปิดเฉพาะฐานข้อมูลด้วย `npm run db:dev`) แล้วรันคำสั่งในอีก terminal ระบบจะถามอีเมล ชื่อ และรหัสผ่าน (อย่างน้อย 8 ตัวอักษร ไม่แสดงบนจอ) ไม่ใช้บัญชีหรือรหัสผ่าน production

```powershell
npm run admin:create
```

เข้าสู่ระบบที่ `/login` เจ้าหน้าที่จะถูกพาไป `/admin` อัตโนมัติ (หรือกดเมนู “จัดการระบบ”) ลูกค้าสมัครได้ที่ `/register` พนักงานให้สมัครเป็นลูกค้าก่อน แล้วเจ้าของร้านเลือกระดับสิทธิ์ที่หน้า “พนักงานและสิทธิ์” (`/admin/staff`)

สิทธิ์มี 3 ระดับ: **SUPER_ADMIN** เจ้าของร้าน (ทุกอย่าง + พนักงาน ตั้งค่าร้าน ประวัติการทำรายการ), **ADMIN** พนักงานดูแลเว็บ (อีเวนท์ การจอง ตรวจเงิน คืนเงิน ตรวจบัตร รายงาน) และ **CUSTOMER** ลูกค้า ฐานข้อมูลที่สร้างจากรุ่นก่อนซึ่งมี role แบบเดิม ให้รัน `npm run db:migrate-roles` หนึ่งครั้ง

| คำสั่ง                                            | ใช้เมื่อ                                                                 |
| ------------------------------------------------- | ------------------------------------------------------------------------ |
| `npm run admin:list`                              | ดูว่ามีบัญชีเจ้าหน้าที่/ผู้ดูแลอีเมลอะไรบ้าง                             |
| `npm run admin:create`                            | สร้างบัญชีผู้ดูแลใหม่ (ไม่เลื่อนสิทธิ์บัญชีลูกค้าที่มีอยู่)              |
| `npm run admin:promote -- you@example.com`        | สมัครที่ `/register` ไว้แล้ว และต้องการให้บัญชีนั้นเป็นผู้ดูแลสูงสุด     |
| `npm run admin:reset-password -- you@example.com` | ลืมรหัสผ่าน (ยังไม่มีรีเซ็ตทางอีเมล) ตั้งรหัสใหม่และออกจากระบบทุกอุปกรณ์ |

คำสั่งเหล่านี้ต้องเข้าถึงฐานข้อมูลได้โดยตรง จึงเป็นช่องทางกู้คืนสำหรับผู้ดูแลเซิร์ฟเวอร์เท่านั้น ทุกคำสั่งบันทึกประวัติใน AuditLog ใช้แบบไม่โต้ตอบได้ด้วย `BOOTSTRAP_ADMIN_EMAIL`/`BOOTSTRAP_ADMIN_PASSWORD` (create), `ADMIN_NEW_PASSWORD` (reset-password) และ `--yes` เพื่อข้ามการยืนยัน

## โปรไฟล์สมาชิก

หลังเข้าสู่ระบบ เปิดเมนูปุ่มสามขีดแล้วเลือก “โปรไฟล์ของฉัน” (`/account`) เพื่อแก้ไขชื่อ เปลี่ยนรหัสผ่าน และดูรายการจองพร้อมลิงก์เปิดบัตรเข้างาน การเปลี่ยนรหัสผ่านต้องกรอกรหัสผ่านปัจจุบัน รหัสผ่านใหม่อย่างน้อย 8 ตัวอักษร และยืนยันให้ตรงกัน เมื่อสำเร็จอุปกรณ์อื่นจะออกจากระบบ ส่วนรายการจองยังเปิดจาก `/account/bookings` ได้ตามเดิม

## ทดลองงานตัวอย่าง

เพิ่มอีเวนต์สมมติพร้อมโปสเตอร์ 3 งานสำหรับดูการ์ดและทดลองจอง โดยเปิด DB ไว้ก่อนแล้วรัน `npm run db:seed:events` คำสั่งนี้ใช้กับฐานข้อมูล localhost และรันซ้ำได้โดยคงอีเวนต์เดิม จากนั้นเปิด `/events` เพื่อดู Red Night Live, Moonlight Acoustic และ Neon After Hours

1. หน้าอีเวนท์มี MONGKOL LIVE SESSION: 8 โต๊ะ (โต๊ะละ 4 สิทธิ์), 12 ที่นั่ง, บัตรยืน 80 สิทธิ์พร้อม Early Bird/Regular ที่ใช้ pool เดียวกัน
2. สมัครลูกค้า → เลือกหน่วยขาย → ยืนยันจอง → ดูยอดและเวลาจริงจากเซิร์ฟเวอร์
3. บัญชีธนาคาร seed เป็นข้อมูลสาธิต **ไม่ต้องโอนเงินจริง** อัปโหลดภาพทดสอบ PNG/JPEG/WebP ไม่เกิน 5 MB แล้วส่งข้อมูลการโอนสมมติ
4. สถานะเปลี่ยนเป็นรอตรวจสอบและยังไม่มีบัตร ผู้ดูแลเข้า `/admin/bookings` เปิดรายการ ตรวจหลักฐาน แล้วกรอกผลตรวจยอดเต็มจำนวนเพื่อทดสอบการอนุมัติ
5. กลับบัญชีลูกค้า กด “ดูบัตรเข้างาน” จากรายละเอียดการจองเพื่อเปิดบัตรจริงที่ระบบออก โต๊ะหนึ่งโต๊ะมี 4 บัตรแยกกัน บัตรเข้างานไม่แสดง QR Code
6. ใช้บัญชีเจ้าหน้าที่ที่ได้รับสิทธิ์งาน เปิด `/admin/check-in` กรอกรหัสบัตรหรือสแกนด้วยกล้อง สแกนซ้ำไม่เพิ่มผู้เข้างาน
7. ทดสอบยกเลิกโดยเจ้าหน้าที่: บัตรถูกเพิกถอนและมีรายการรอคืนเงิน หากบันทึกหลักฐานคืนเงินแล้วจึงเป็น REFUNDED ปุ่มเว็บไม่โอนเงิน

## ผังและการเปิดขายงานใหม่

ขนาดรูปแนะนำ: โปสเตอร์ 1,200 × 1,800 px (2:3), โลโก้ 900 × 300 px (3:1) หน้าจัดการแสดงขนาดรูปที่เลือกและพรีวิวตามกรอบใช้งานจริง ดูตำแหน่งรูปอื่นและแนวทางออกแบบใน [คู่มือขนาดรูปภาพ](docs/design/image-guide.md)

หน้าเพิ่ม/แก้ไขอีเวนท์รองรับอัปโหลดและพรีวิวโปสเตอร์จากเครื่อง ส่วนหน้า “ตั้งค่าธุรกิจ” รองรับโลโก้ร้าน (SUPER_ADMIN เท่านั้น) เลือกรูป PNG/JPEG/WebP ไม่เกิน 5 MB เปลี่ยนรูปหรือนำรูปออกแล้วกดบันทึกข้อมูลจึงมีผลกับหน้าลูกค้า ยังใช้ URL รูปเดิมได้ผ่าน “ใช้ลิงก์รูปภาพแทน” รูปที่อัปโหลดเป็นรูปสาธารณะ เก็บแยกใน `STORAGE_DIRECTORY/public-images` และต้องสำรองพร้อม volume เดิม ระบบไม่ลบไฟล์เก่าอัตโนมัติเพื่อไม่ให้รูปที่ใช้ร่วมกันเสียหาย

สร้างงานแบบร่าง → สร้างโซน TABLE/SEAT/GENERAL_ADMISSION → เพิ่มหน่วยขายหรือประเภทบัตร → เปิด layout editor ผูกวัตถุเข้ากับหน่วยขาย → บันทึกและเผยแพร่ผัง → เปิดขายงาน

ทุกหน่วย TABLE/SEAT ต้องอยู่ในผังก่อนเผยแพร่ ส่วน GA ใช้โซนและโควตาร่วม แก้ผังเป็นเวอร์ชันใหม่โดยไม่เปลี่ยนผังที่รายการจองเก่าอ้างอิง โครงสร้างหน่วยขายเพิ่ม/ลบได้เฉพาะร่างงาน การเปลี่ยนราคาภายหลังไม่แก้ snapshot การจองเดิม

- **ทำซ้ำเป็นรอบใหม่**: ปุ่ม “ทำซ้ำ” คัดลอกโซน หน่วยขาย ราคา ประเภทบัตร และร่างผังเป็นงานฉบับร่างใหม่ (ไม่คัดลอกการจอง) จากนั้นเผยแพร่ผังและเปิดขาย
- **แก้โครงสร้างงานที่เปิดขายแล้ว**: ปิดการขาย → “กลับเป็นฉบับร่าง” (ทำได้เมื่อไม่มีการจองที่ใช้งานอยู่) → แก้ → เผยแพร่ผัง → เปิดขาย
- **ลบ**: โซน/หน่วยขาย/ประเภทบัตรลบได้ในร่างงานเมื่อไม่มีประวัติการจอง ลบหน่วยขายจะนำวัตถุที่ผูกออกจากร่างผังด้วย อีเวนท์ลบได้เมื่อไม่ได้เปิดขายอยู่และไม่มีการจองเลย นอกนั้นใช้ยกเลิก/ปิดหน่วย/ปิดประเภทบัตรเพื่อเก็บประวัติ
- **ประเภทบัตร GA**: เปลี่ยนช่วงขายหรือปิดขายบางราคา (เช่น จบ Early Bird) ได้ระหว่างเปิดขาย มีผลกับการจองใหม่เท่านั้น

การยกเลิกงานประมวลผลครั้งละ 25 การจองและรายงาน `remaining` ต้องดำเนินต่อจนเป็น 0 งานถูกปิดรับการจองตั้งแต่เริ่มยกเลิก

## Atlas หรือ Docker

ใช้ MongoDB Atlas replica set แล้วใส่ `DATABASE_URL` ของฐานข้อมูลพัฒนาแยกจาก production จำกัด IP และบัญชีตามสิทธิ์ที่จำเป็น จากนั้นใช้ validate/generate/db push/seed ตามข้างต้น

Docker ทางเลือก: เปิด Docker Desktop แล้ว `docker compose up -d` จากนั้นเปลี่ยน URL เป็นค่าตาม `docker-compose.yml` และเริ่ม replica set ตาม healthcheck ของไฟล์ compose ห้ามเปิด `db:dev` และ Docker บนพอร์ตเดียวกัน

## งานหมดเวลาและคิวตรวจ

เรียก `POST /api/jobs/expire` จาก scheduler ทุกหนึ่งนาทีพร้อม `Authorization: Bearer <JOB_SECRET>` ไม่มี cookie endpoint ประมวลผลครั้งละ 100 รายการและตอบ `more` ให้เรียกต่อจน false รวมข้อมูลคิวตรวจเกินกำหนดด้วย การสร้าง/อ่านการจองตรวจหมดเวลาฝั่งเซิร์ฟเวอร์เพิ่มเติม ไม่อาศัย cron เพียงอย่างเดียว

## โครงสร้าง

| ตำแหน่ง               | หน้าที่                                                     |
| --------------------- | ----------------------------------------------------------- |
| `src/app`             | หน้าลูกค้า บัญชี หลังบ้าน และ Route Handlers `/api`         |
| `src/server/services` | กฎการจอง inventory payment refund layout check-in และรายงาน |

| `docs`                | ข้อกำหนด API พจนานุกรมข้อมูล และผลรับมอบ                    |

## ข้อจำกัดการนำไปใช้จริง

ยังไม่ได้ deploy หรือเชื่อมธนาคาร/mail service ไม่มีการกู้รหัสผ่านทางอีเมลจนกว่าจะตั้ง mail service จริง หลักฐานต้องอยู่บน private persistent volume; ไม่เหมาะกับ filesystem ชั่วคราวของ serverless ต้องเปลี่ยน storage adapter ก่อนใช้ลักษณะนั้น เก็บและสำรอง `TICKET_ENCRYPTION_KEY` อย่างปลอดภัย กุญแจหายจะเปิดบัตรเดิมไม่ได้

ต้องตั้งค่าข้อมูลธุรกิจ บัญชีรับเงินจริง HTTPS การสำรองข้อมูล scheduler และ reverse proxy ให้ตรงสภาพแวดล้อมก่อนเปิดสาธารณะ ผลตรวจในเครื่องไม่ใช่ผลรับรอง production ดูรายการที่ผ่าน/ยังไม่ได้ตรวจในรายงานรับมอบ
